Worked Example — Writing Then Reading Student Scores

Problem: Store two students' first name, middle initial, last name, and score in a file named scores.txt, then read the file back and display each record.

Reasoning, step by step

  1. Include the header and declare an output stream. 
    // ofstream lets us write to a file the same way we write to cout
#include <fstream>
using namespace std;

ofstream output;

    We reach for ofstream specifically because this step only writes — using fstream here would work too, but it would ask C++ to support reading it never needs.

  2. Open the file and immediately check that it succeeded. 
    output.open("scores.txt");

    Opening with no mode flags defaults to ios::out, which — this is the detail students most often miss — silently erases any existing content in scores.txt the moment open() runs, before a single byte is written.

  3. Write each record using the same << syntax used for console output. 
    output << "John T Smith " << 90 << endl;
output << "Eric K Jones " << 85 << endl;

    Each field is separated by whitespace on purpose — later, when we read this file back with >>, that operator delimits tokens on whitespace, so the write format has to match how we intend to read it.

  4. Close the stream. 
    output.close();

    Closing flushes any buffered data to disk. Skipping this step is one of the most common sources of "my file looks empty" bugs (see the misconception below for the nuance here).

  5. Open a second stream to read the file back. 
    ifstream input;
input.open("scores.txt");
if (input.fail()) {
    cout << "File does not exist" << endl;
    return 1;
}

    Checking fail() right after open() is the standard, idiomatic way to confirm the file actually exists before trying to read from it.

  6. Read the fields back with >>, in the same order they were written. 
    string firstName, lastName;
char mi;
int score;

while (input >> firstName >> mi >> lastName >> score) {
    cout << firstName << " " << mi << " "
         << lastName << " " << score << endl;
}
input.close();

    Placing the whole extraction chain as the loop condition is deliberate: >> returns the stream itself, which converts to false the moment a read fails (including hitting end-of-file), so the loop stops exactly when there is nothing left to read — no separate eof() check needed in this pattern.

Your Turn (Apply)

Using the same pattern, write a program that stores three product records — a product name (string), a category code (a single character, e.g. 'E' for electronics), and a price (double) — into a file named inventory.txt, then reads the file back and prints each product with its price formatted to two decimal places.

Reveal a model solution 
#include <fstream>
#include <iomanip>
using namespace std;

int main() {
    ofstream output("inventory.txt");
    output << "Keyboard " << 'E' << " " << 24.99 << endl;
    output << "Notebook " << 'S' << " " << 1.49  << endl;
    output << "Monitor "  << 'E' << " " << 129.0 << endl;
    output.close();

    ifstream input("inventory.txt");
    if (input.fail()) { return 1; }

    string name; char cat; double price;
    while (input >> name >> cat >> price) {
        cout << name << " (" << cat << ") $"
             << fixed << setprecision(2) << price << endl;
    }
    input.close();
    return 0;
}

Notice the write order (name, char, double) exactly matches the read order — the same discipline used in the worked example above.

Real-World Application

Case: Lab Check-In Kiosk. Delta College's CS lab wants a simple kiosk program: every time a student badges in, the program appends their student ID and a timestamp to attendance_log.txt. The log must never lose a previous day's entries, even though the kiosk program is started fresh each morning.

Design questions this raises:

  • Which open mode combination prevents the previous day's log from being erased on startup?
  • At the end of the semester, a script re-opens the log to total each student's visits — how should it detect that it has reached the last entry?
  • What should the program do if attendance_log.txt doesn't exist yet on a brand-new lab computer?
Reveal the design rationale

Open with ios::out | ios::app — app forces every write to the end of the file regardless of where the file pointer would otherwise sit, so old entries are never overwritten. To sum visits later, loop while extraction succeeds (as in the worked example) rather than pre-checking eof(), since eof() is only reliably true after a read has already failed. Finally, call fail() immediately after open() — but here a failed open should create the file rather than report an error, since a missing log on a new machine is expected, not exceptional.

Common Misconceptions

⚠ Misconception 1

"If I forget to call close(), my program will crash or lose the file entirely."

Why it's wrong: The ofstream/ifstream destructor closes the stream automatically when the object goes out of scope, so the program itself won't crash. Correct reasoning: the real risk is that output may be sitting in an internal buffer that hasn't been flushed to disk yet — so if the program terminates abnormally, or if another part of the same program tries to reopen and read that file before the stream object is destroyed, the data can appear missing or incomplete. Calling close() explicitly removes that risk instead of relying on timing.

⚠ Misconception 2

"Text files and binary files are stored in fundamentally different ways by the computer."

Why it's wrong: Every file on disk is stored as binary — there is no separate "text storage format" at the hardware level. Correct reasoning: text I/O is a layer of abstraction built on top of binary I/O that encodes and decodes characters (e.g., the digits of 199 as three separate character codes). Binary I/O skips that encoding step and writes the value's raw byte representation directly (199 as the single byte C7 in hex) — the difference is in interpretation, not in whether the underlying storage is "binary."

⚠ Misconception 3

"The >> operator is always a safe way to read any text data from a file."

Why it's wrong: >> stops reading at the first whitespace character. Correct reasoning: a value like a city name — "San Francisco" — contains an internal space, so >> would split it into two separate reads ("San" and "Francisco") instead of one string. getline(input, str, delimitChar) reads through embedded whitespace up to a chosen delimiter, which is the correct tool whenever a field may itself contain spaces.
