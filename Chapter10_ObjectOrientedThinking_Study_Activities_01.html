Object-Oriented Thinking

Six sections build from passing objects to functions up through class design and constructor initializer lists. Each section ends with a quick self-check. Then head to Flashcards, the Quiz, or the Matching activity to practice.

Just like primitive types, C++ objects are passed by value by default \u2014 a copy of the object is made for the function's parameter. Adding & to the parameter switches to pass by reference, which passes the original object's memory location instead of a copy.

🧩 Worked Example \u2014 Same Function, Two Passing Mechanisms

Both versions start the same way: Circle c1; (radius = 1), then call a function that sets the radius to 12.1.

By Valuevoid printByValue(Circle c1) \u2014 c1 inside the function is a copy. Setting its radius to 12.1 only changes the copy. Output: inside the function, radius is 12.1 \u2014 but back in main(), c1.print() still shows radius is 1.
By Referencevoid printByReference(Circle &c1) \u2014 c1 inside the function is the original object. Setting its radius to 12.1 changes the real thing. Output: back in main(), c1.print() now shows radius is 12.1.
TakeawayThe only difference in the code is one & symbol in the parameter \u2014 but it completely changes whether the caller's object is affected.
⚠️ Common Misconception

"Objects are always passed by reference in C++ since they're complex data types." Not true. Unless a parameter is explicitly declared with &, C++ objects are passed by value \u2014 exactly like an int or double. A full copy of the object (all its data fields) is made for the function. This differs from some other languages, so it's worth checking carefully in C++.

✔️ Quick Self-Check

1. A function has the parameter Circle c1 (no &). If it changes c1's radius, what happens to the original object in main()?

2. Which parameter declaration passes an object by reference?

An array can hold objects just like it holds primitives: Circle circleArray[3] = {Circle(3), Circle(4), Circle(5)}; creates three Circle objects in one array, ready to loop over (e.g., to sum up a total area).

Static (Class) Variables

A static variable belongs to the class itself, not to any one object. There is only ever one copy, shared by every instance.

🧩 Worked Example \u2014 Counting Circle Objects
DeclareInside the class: static int numberOfObjects; and static int getNumberOfObjects();
DefineOutside the class, in the .cpp file: int Circle::numberOfObjects = 0; \u2014 this is where the single shared copy actually lives.
UpdateEvery constructor includes numberOfObjects++; \u2014 so each time any Circle is constructed, the one shared counter goes up by one.
AccessBecause it belongs to the class, you can call Circle::getNumberOfObjects() directly \u2014 no object required.
⚠️ Common Misconception

"Each object has its own copy of a static variable, just like it does for instance variables." The opposite is true. Instance variables (like radius) get a fresh copy per object. Static variables get exactly one copy, shared by the entire class \u2014 that's precisely what makes them useful for things like counting how many objects have been created.

✔️ Quick Self-Check

1. Three Circle objects are created. How many copies of numberOfObjects exist in memory?

2. Which correctly calls a static function without creating an object first?

Placing const at the end of a member function's header \u2014 e.g. double getArea() const; \u2014 tells the compiler this function is not allowed to modify any of the object's data fields. It's a promise the compiler enforces for you.

🌍 Real-World Application \u2014 Evolving a Body Mass Index (BMI) Program

BMI is calculated as weightInKilograms / heightInMeters², classified as: under 18.5 = Underweight, 18.5\u201325.0 = Normal, 25.0\u201330.0 = Overweight, 30.0+ = Obese. The same program evolves across three solutions:

Solution 1All the code lives inside main(). It works once, but none of it can be reused for a second person without copy-pasting.
Solution 2Break the logic into functions (the procedural paradigm). Now the BMI calculation is reusable \u2014 but weight, height, name, and age are passed around as separate, uncoupled parameters with no guarantee they belong together.
Solution 3Create a BMI class (the object-oriented paradigm). Now weight, height, name, and age are bundled into one object, along with the functions that operate on them \u2014 reusable and naturally coupled.

This is the core difference between the two paradigms: procedural code keeps data and functions separate; object-oriented code ties them together in an object, which tends to be easier to reuse and maintain.

✔️ Quick Self-Check

1. A person weighs 70 kg and is 1.75 m tall. Their BMI is 70 / 1.75² ≈ 22.9. How is that classified?

2. What is the main advantage Solution 3 (the BMI class) has over Solution 2 (functions alone)?

GuidelineWhat it means
CohesionA class should describe a single entity, or a tightly related set of operations \u2014 split an overloaded class into several if needed
ConsistencyFollow standard naming conventions and style consistently throughout the class
EncapsulationKeep data fields private; expose them only through get/set functions where appropriate
ClarityDesign functions so they work correctly regardless of the order the user calls them in
CompletenessSupport the range of ways different users might reasonably want to use the class

Clarity in Action \u2014 the Loan Class

A Loan class has setLoanAmount(), setNumberOfYears(), and setAnnualInterestRate(). A well-designed class lets a user call these in any order or combination \u2014 the class shouldn't silently break if setNumberOfYears() happens to be called before setLoanAmount().

Completeness in Action \u2014 the string Class

C++'s built-in string class has more than 20 member functions \u2014 far more than any single program needs \u2014 because it's designed to serve a huge range of different applications, not just one.

⚠️ Common Misconception

"As long as a class compiles and produces the right output, its design doesn't really matter." A class can work correctly today and still be a poor design \u2014 hard to reuse, easy to misuse, or painful to extend later. Guidelines like cohesion and encapsulation aren't about correctness; they're about keeping a class maintainable and reusable as a program (and the people working on it) grows.

Composition is a "has-a" relationship: one class contains another as a data field, instead of duplicating that class's logic.

🧩 Worked Example \u2014 Designing a Cylinder Class

A Cylinder needs a circular base and a height, and should be able to compute its surface area and volume.

First draftA naive UML might give Cylinder its own radius field and re-implement circle-area math from scratch \u2014 duplicating logic the Circle class already has.
Better designInstead, give Cylinder a data field base : Circle plus height : double. Cylinder now reuses Circle's existing getArea() for its top and bottom, rather than reinventing it.
ResultSurface area = 2 \u00d7 (Circle's area) + (circumference \u00d7 height). Cylinder "has a" Circle \u2014 that's the composition relationship.
✍️ Your Turn \u2014 Apply It

A Car class needs to track its Engine (with its own horsepower and fuel type). Sketch the composition relationship: what data field would Car have, and of what type? Then reveal a model answer.

Car would have a data field like engine : Engine \u2014 the Car class "has a" Engine object, the same way Cylinder "has a" Circle. Car can then call the Engine object's own functions instead of duplicating engine logic inside Car itself.

Object data fields are not automatically initialized the way local variables sometimes are. Two ways to set an object data field's starting value in a constructor:

StyleExample
Constructor initializerCircle::Circle() : radius(1) { }
Assignment in the bodyCircle::Circle() { radius = 1; }

Both work the same for simple cases \u2014 but an initializer list is required when a data field's own class has no no-arg constructor, since there'd be no way to construct that field before the body even runs.

🌍 Real-World Application \u2014 The StackOfIntegers Class

A stack stores items last-in, first-out (LIFO). Compilers use exactly this structure to manage function calls: when a function is called, its parameters and local variables are pushed onto a stack; when it returns, that space is popped off. If function A calls function B, B's data sits on top of A's until B finishes \u2014 which is why the most recently called function always finishes first.

✍️ Your Turn \u2014 Design It (Create)

Design the public interface for a StackOfIntegers class. List the function signatures you'd need to push a value, pop a value, peek at the top without removing it, and check whether the stack is empty. Then reveal a model answer.

void push(int value); \u2014 adds a value to the top
int pop(); \u2014 removes and returns the top value
int peek() const; \u2014 returns the top value without removing it
bool isEmpty() const; \u2014 reports whether the stack has anything in it
peek() and isEmpty() are natural candidates for const, since neither should modify the stack's contents.
