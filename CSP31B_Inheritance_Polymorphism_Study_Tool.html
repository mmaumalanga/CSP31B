Inheritance and polymorphism

Inheritance lets a new class reuse and specialize an existing one. Polymorphism lets one piece of code work with many related types and still call the right function for each. 1. Relating classes: is-a vs has-a

RememberUnderstand

Suppose you already have a working RectangleType class and now need a BoxType with a length, width, and height. Rewriting length and width from scratch wastes time. C++ gives you two ways to reuse the existing class:

RelationshipMeaningHow it looks in C++Test sentence
Composition (aggregation)One class contains an object of another as a data member.class BoxType { RectangleType base; double height; };A box has a rectangle as its base.
InheritanceA new (derived) class is a specialized version of an existing (base) class.class BoxType : public RectangleType { double height; };A circle is a geometric object.

With inheritance, the existing class is the base class (supertype, parent) and the new class is the derived class (subtype, child). The derived class inherits the base class's data members and member functions, then adds or changes what it needs.

GeometricObject
- color : string
- filled : bool
+ getColor() : string
+ isFilled() : bool
+ toString() : string
◁── derived from ──
Circle
- radius : double
+ getRadius() : double

class Circle : public GeometricObject     // "Circle is a GeometricObject"
{
public:
  Circle();
  Circle(double radius, const string& color, bool filled);
  double getRadius() const;
  double getArea() const;
  string toString() const;
private:
  double radius;                           // color and filled are inherited
};

Access: public, protected, private

Base class member is…Inside the base classInside a derived classOutside code (main)
publicYesYesYes
protectedYesYesNo
privateYesNo (use public getters/setters)No

The word public in class Circle : public GeometricObject is the member access specifier. It can be public, protected, or private; if you leave it out, it defaults to private. You'll almost always want public.

Common misconception: "A derived class can use the base class's private data directly because it inherited it."

A Circle object does contain color and filled, but Circle's member functions can't name them. Writing color = "red"; inside Circle is a compile error.

Correct reasoning: private means private to the class that declared it, even from its children. Use the base class's public functions (setColor("red")), or declare the member protected in the base class if derived classes truly need direct access.

Also remember that "is a" only goes one way: every Circle is a GeometricObject, but not every GeometricObject is a Circle.

2. Worked example: deriving BoxType

UnderstandApply

We'll derive BoxType from RectangleType, exposing the reasoning at each step. RectangleType already has private length and width, a constructor RectangleType(double l, double w), and functions area(), perimeter(), and print().

Worked example: class BoxType : public RectangleType
  1. Check the relationship. Is a box a rectangle? We treat the box as a rectangle (its base) extended upward, so it has everything a rectangle has plus a height. Reason: inheritance fits when the new class is a specialized version of the old one. Here we reuse length, width, and perimeter() for free.
  2. Add only what's new. One data member, height, and one new function, volume(). Reason: length and width are already inherited. Declaring them again would create a second, hidden copy.
  3. Call the base constructor in the initializer list. BoxType(double l, double w, double h) : RectangleType(l, w) Reason: constructors are not inherited, and BoxType can't touch the private length and width. The base class must initialize its own part, and it runs first.
  4. Redefine area() so it returns the surface area of a box, reusing the rectangle's version with RectangleType::area(). Reason: same name and parameters as the base version means redefining. The scope resolution operator :: reaches the base version; without it, area() would call itself forever.
  5. Use inherited getters for private data. getLength() and getWidth() are public in the base, so BoxType may call them.
class BoxType : public RectangleType
{
public:
  BoxType() : RectangleType(), height(0) { }
  BoxType(double l, double w, double h)
    : RectangleType(l, w)                  // base part built first
  { height = (h >= 0) ? h : 0; }

  double area() const                      // REDEFINES RectangleType::area()
  {
    return 2 * RectangleType::area()        // top + bottom
         + height * perimeter();          // four sides (inherited function)
  }
  double volume() const                    // new in BoxType
  { return RectangleType::area() * height; }

private:
  double height;
};
Trace it with BoxType box(2, 3, 4);
RectangleType(2, 3) runs first → length=2, width=3  |  then BoxType body → height=4
box.area() = 2·(2·3) + 4·(2·(2+3)) = 12 + 40 = 52  |  box.volume() = 6·4 = 24

Constructor and destructor chaining

Building a derived object calls constructors from the top of the chain down: base first, then derived. Destroying it runs destructors in the reverse order: derived first, then base. If you add cout statements to each:

// { BoxType box(2, 3, 4); }  prints:
RectangleType constructor
BoxType constructor
BoxType destructor
RectangleType destructor

Why this order?

The derived part is built on top of the base part, so the base must exist first. When tearing down, the derived destructor may still use base members, so the base must be destroyed last.

Common misconception: "If I don't call a base constructor, the base part just isn't initialized."

A derived constructor always runs a base constructor. If you don't name one in the initializer list, C++ silently calls the base's no-arg constructor. If the base has none, you get a compile error:

class Fruit { public: Fruit(int id) { } };      // no no-arg constructor
class Apple : public Fruit { public: Apple() { } };  // ERROR: calls Fruit(), which doesn't exist

Correct reasoning: either call Apple() : Fruit(0) { } explicitly, or give any class designed to be extended a no-arg constructor.

Your turn: derive Cylinder from Circle

Circle has a constructor Circle(double radius) and a public getArea() that returns πr². Write a class Cylinder that publicly inherits from Circle, adds a private height, has a constructor Cylinder(double r, double h), and a getVolume() that returns base area × height.

    class Cylinder : public Circle
{
public:
  Cylinder(double r, double h) : Circle(r), height(h) { }
  double getVolume() const { return getArea() * height; }
private:
  double height;
};
    Trace: Cylinder c(1, 10); → Circle(1) runs first, then height = 10 → volume = π·1²·10 ≈ 31.42. getArea() is inherited, so no Circle:: prefix is needed here because Cylinder didn't redefine it.

    3. Polymorphism and virtual functions

    UnderstandApplyAnalyze

    Polymorphism means a variable of a supertype can refer to a subtype object. Because every Circle is a GeometricObject, a function with a GeometricObject parameter accepts a Circle or a Rectangle. Writing one function that works for a whole family of types is called generic programming.

    Static binding vs dynamic binding
    
    
    Matching a function signature and binding its implementation are two separate steps:
    
    
    
      
    Static binding (compile time)
    For a non-virtual function, the compiler picks the implementation from the declared type of the variable. g is declared GeometricObject&, so GeometricObject::toString() runs every time.
    
      
    Dynamic binding (run time)
    For a virtual function reached through a reference or pointer, C++ picks the implementation from the actual type of the object at run time.
    
    
    
    
    Two requirements for dynamic binding: the function is declared virtual in the base class, and the variable holds the object's address (a reference or pointer). Once a function is virtual in the base, it's automatically virtual in every derived class.
    

    
    
      
    Common misconception: "Marking a function virtual is enough for polymorphism."
    
      
    If you pass the object by value, void display(GeometricObject g), the Circle is copied into a brand-new GeometricObject. The Circle-specific part is sliced off, so g.toString() returns "Geometric Object" even with virtual.
    
      
    Correct reasoning: dynamic binding needs the original object, so pass by reference (const GeometricObject& g) or pointer (GeometricObject* p).
    
    
    

    
    Redefining, overriding, and overloading
    
    
    
      
    TermWhereSignatureBinding
    
      
    OverloadingUsually the same classSame name, different parametersStatic
    
      
    RedefiningBase and derivedSame signature and return typeStatic (non-virtual)
    
      
    OverridingBase and derivedSame signature, base version is virtualDynamic
    
    
    
    
    C++11 adds two helpful keywords. Writing override after a derived function asks the compiler to confirm it really overrides a base virtual function, which catches typos. Writing final prevents further overriding in classes derived from it.
    
    
    class Circle : public GeometricObject
{
public:
  string toString() const override;          // compiler checks this
  string tostring() const override;          // ERROR: nothing to override (typo caught)
};
    
    
    Why not make every function virtual? Dynamic binding costs a little extra time at run time. Make a function virtual when derived classes are expected to override it.

    4. Abstract classes and casting
    UnderstandAnalyzeEvaluate
    

    
    Abstract classes and pure virtual functions
    
    
    Every geometric object has an area and a perimeter, so getArea() and getPerimeter() belong in GeometricObject. But the base class can't compute them, because the formula depends on the shape. Declare them as pure virtual functions with = 0:
    
    
    class GeometricObject
{
public:
  GeometricObject(const string& color, bool filled);   // abstract classes CAN have constructors
  string getColor() const;                            // and ordinary functions/data
  virtual double getArea() const = 0;                  // pure virtual: no body here
  virtual double getPerimeter() const = 0;
  virtual ~GeometricObject() { }                        // safe cleanup through base pointers
private:
  string color;
  bool filled;
};
    
    
    A class with at least one pure virtual function is an abstract class. You can't create objects of it, but you can use it as a parameter type, reference, or pointer. A derived class must override every pure virtual function to become concrete; otherwise it's abstract too.
    
    
    
      
    Common misconception: "An abstract class is just an empty interface. It can't have data or constructors."
    
      
    GeometricObject above is abstract, yet it stores color and filled, has a constructor, and implements getColor(). What you can't do is write GeometricObject g("red", true);.
    
      
    Correct reasoning: "abstract" means "incomplete," not "empty." The constructor still runs, called from Circle's initializer list, to set up the shared part of every shape.
    
    
    

    
    
      
    Real-world application: a grocery store checkout
    
      
    A supermarket's point-of-sale system handles items priced in different ways: packaged goods at a fixed price, produce by weight, and dairy with a bottle deposit. An abstract base class lets one checkout loop total the whole cart:
    
      
    class GenericItem {                          // abstract
public:
  GenericItem(const string& n) : name(n) { }
  virtual double getPrice() const = 0;
  virtual ~GenericItem() { }
protected:
  string name;
};
class ProduceItem : public GenericItem {     // "produce is a generic item"
public:
  ProduceItem(const string& n, double lbs, double perLb)
    : GenericItem(n), pounds(lbs), pricePerLb(perLb) { }
  double getPrice() const override { return pounds * pricePerLb; }
private:
  double pounds, pricePerLb;
};
// DairyItem, PackagedItem ... each override getPrice()

double total = 0;
for (GenericItem* item : cart)                 // vector<GenericItem*> cart
  total += item->getPrice();                   // dynamic binding picks the right formula
    
      
    When the store adds a new item type, like bakery items sold by the dozen, programmers write one new derived class. The checkout loop doesn't change at all. That's the practical payoff of polymorphism, and the same design shows up in payroll systems (hourly vs salaried employees) and games (every enemy has its own update()).
    
    
    

    
    Upcasting and downcasting
    
    
    Upcasting (derived pointer to base pointer) is always safe and happens implicitly: GeometricObject* p = new Circle(1);. Downcasting (base pointer to derived pointer) must be explicit, because the object might not actually be that type.
    
    
    void displayGeometricObject(GeometricObject& g)
{
  GeometricObject* p = &g;
  Circle* c = dynamic_cast<Circle*>(p);    // checked at run time
  if (c != nullptr)                          // nullptr means "not a Circle"
    cout << "The radius is " << c->getRadius() << endl;
  cout << "The area is " << g.getArea() << endl;
}
    
    
    
      
    static_cast
    Converts at compile time with no check. static_cast<Circle*>(p) on a Rectangle compiles and then produces garbage or a crash.
    
      
    dynamic_cast
    Checks the actual type at run time and returns nullptr if the cast is invalid. It requires the class to have at least one virtual function.
