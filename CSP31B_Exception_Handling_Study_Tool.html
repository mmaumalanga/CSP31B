    1. Exception Basics: try, throw, catch

    RememberUnderstandApply

    An exception is an undesirable event detected while a program runs, such as a bad argument, a missing file, or an index that is out of range. Exception handling lets the code that detects a problem be separate from the code that decides what to do about it.

    The problem: dividing by zero

    The first quotient program from the slides crashes when the divisor is 0. The program ends with exit code 136 instead of printing a message.

    Enter two integers: 5 0

...Program finished with exit code 136
    

  
    
    
    !Common misconception #1
    
    
    "Integer division by zero throws a C++ exception, so a try/catch around a / b will catch it."
    
    
    Why it's wrong: C++ does not throw anything for integer division by zero. It is undefined behavior; on most systems the operating system kills the program (the exit code 136 above is the SIGFPE signal). A catch block never runs. Correct reasoning: you must check the divisor yourself and throw an exception explicitly. Only then is there something to catch.
    
  
    

  
    The template
    
  
    
  
    
    
    try
    Wraps code that might fail. If nothing is thrown, every catch block is skipped.
    
    
    throw
    Signals the problem by sending an object (an int, a string, or an exception object) out of the current code.
    
    
    catch
    Handles one type of exception. The parameter type decides what it catches. The parameter name may be omitted.
    
  
    

  
    
    WORKED EXAMPLE
    
    Making quotient() report the error to its caller
    
    
    Goal: the function should not decide how to handle the error. It should report it, and let main() decide. Follow the reasoning one step at a time.
    
    
    5
Error: Divisor cannot be zero
Execution continues
    
    
      
      
    1. Find the failure condition. number2 == 0 is the only input that makes the division impossible.Always name the exact condition before writing any exception code.
      2. 
      
    2. Detect it where it happens. The check goes inside quotient(), right before the division.The function knows the rule ("divisor can't be zero") but not how the program wants to respond.
      3. 
      
    3. Throw an object that describes the problem. throw invalid_argument("Divisor cannot be zero");invalid_argument (from <stdexcept>) fits: the caller passed an illegal argument. Its message is available later through what().
      4. 
      
    4. Wrap the risky call in try. In main(), both calls to quotient() go inside the try block.Only exceptions thrown from inside a try block (directly or from functions it calls) can be caught by its handlers.
      5. 
      
    5. Catch by const reference. catch (const invalid_argument& ex)A reference avoids copying the object and keeps the real derived type (see Section 4).
      6. 
      
    6. Trace the control flow. quotient(45, 9) prints 5. quotient(5, 0) throws, so the rest of the try block (including "never") is skipped, the handler prints the message, and execution continues after the last catch.After a throw, control never returns to the line after the throw.
      7.

    2. Standard Exception Classes
    
  
    RememberUnderstandApply
    
  
    C++ supplies a hierarchy of exception classes. The base class is exception (header <exception>). Every class in the hierarchy overrides the virtual function what(), which returns a C-string describing the error.
    
  
    exception                      base class; what()
├── logic_error                errors the program could have prevented
│   ├── invalid_argument       illegal argument, e.g. stoi("abc")
│   ├── out_of_range           bad index or position, e.g. v.at(99)
│   ├── length_error           exceeds a maximum allowed size
│   └── domain_error           input outside a math function's domain
├── runtime_error              errors detectable only while running
│   ├── overflow_error
│   ├── underflow_error
│   └── range_error
├── bad_alloc                  new cannot allocate memory
└── bad_cast                   failed dynamic_cast to a reference
    
  
    logic_error, runtime_error and their subclasses are in <stdexcept>; bad_alloc is in <new>; bad_cast is in <typeinfo>.
    

  
    Example from the slides: substr()
    
  
    25
s1 = Joaquin Delta College
out_of_range caught
    

  
    
    
    !Common misconception #2
    
    
    "sentence.substr(4, 30) goes past the end of the string, so it throws length_error."
    
    
    Why it's wrong: the second argument is a maximum count. If it runs past the end, substr() simply stops at the end, so substr(4, 30) returns "Joaquin Delta College" with no exception. Correct reasoning: only a starting position greater than length() is an error, and it throws out_of_range, not length_error. That is why substr(31, 10) on a 25-character string lands in the out_of_range handler.
    
  
    

  
    More library functions that throw

    v.at(i) vs v[i]
    at() checks the index and throws out_of_range. The [] operator does not check: a bad index is undefined behavior.
    
    
    new and bad_alloc
    The slides' BadAllocExceptionDemo allocates huge arrays in a loop until new fails and throws bad_alloc.
    
  
    

  
    

    



    
  
    3. Creating Your Own Exception Classes
    
  
    UnderstandApplyAnalyze
    
  
    Use the standard classes whenever they describe the problem. When they don't, write your own. Any class can be thrown, but the best practice from the slides is to derive from exception or one of its subclasses so your class gets what() and can be caught by general handlers.
    
  
    
    
    1. Choose a base
    logic_error for preventable errors, runtime_error for conditions known only at run time.
    
    
    2. Pass a message up
    The constructor calls the base constructor with a message: : logic_error("Invalid triangle").
    
    
    3. Add useful data
    Store the values that caused the problem and provide getters, like getSide1() in TriangleException.
    
  
    

  
    
    
    $Real-world application: a bank account
    
    
    An ATM must never let a withdrawal make the balance negative, and it must tell the customer how much they are short. A custom exception can carry that extra data.
    
  
    

  
    
    WORKED EXAMPLE
    
    Designing InsufficientFunds
    
    
    
    
    Withdrew 40, balance 60
Rejected: Amount must be positive
Insufficient funds: short by 30
    
    
      
      
    1. Pick the base class. Not having enough money depends on the balance at run time, so derive from runtime_error.A negative amount is different: the caller could have prevented it, so it uses the standard invalid_argument (a logic_error).
      2. 
      
    2. Pass a message to the base constructor. : runtime_error("Insufficient funds") in the initializer list.Now what() works without writing it yourself.
      3. 
      
    3. Store the data the handler will need. balance and amount become private members, with getShortfall() as a const getter.The catch block can report "short by 30" instead of a vague message.
      4. 
      
    4. Throw at the point of detection. withdraw() checks the two rules and throws a different type for each.Different types let the caller respond differently to each problem.
      5. 
      
    5. Catch each type separately. One handler per type, each by const reference, inside the loop.Because the try/catch is inside the loop, one failed withdrawal doesn't stop the rest: this is recover and continue.
      6.

    Complete TriangleException
    
    
    A triangle is invalid when one side is not shorter than the sum of the other two. The program could have prevented this, so pick a matching base class.
    

    class TriangleException : public  {
public:
    TriangleException(double s1, double s2, double s3)
        : ("Invalid triangle"),
          side1(s1), side2(s2), side3(s3) {}
    double getSide1()  { return side1; }
private:
    double side1, side2, side3;
};

// inside the Triangle constructor:
if (!isValid(side1, side2, side3))
     TriangleException(side1, side2, side3);
    
    
    
    
    
  
    

  
    
    
    iAbout writing your own what()
    
    
    The slides' first divByZero class defined string what(). That works when you catch divByZero directly, but it does not override exception::what(), whose exact signature is const char* what() const noexcept. If you want catch (const exception& e) to show your message, either derive from logic_error/runtime_error and pass the message to its constructor (easiest), or override with that exact signature.
    
  
    

  
    

    



    
  
    4. Multiple Catches, Propagation, and Rethrowing
    
  
    UnderstandApplyAnalyze
    
  
    Multiple catch blocks
    
  
    One try block can be followed by several handlers. C++ checks them top to bottom and runs the first one whose type matches. A handler for a base class also matches every derived class.
    
  
    logic_error handler
    

  
    
    
    !Common misconception #3
    
    
    "C++ picks the catch block that matches the exception best, so the order doesn't matter."
    
    
    Why it's wrong: C++ takes the first match, not the best. Since invalid_argument is a logic_error, the base-class handler above grabs it and the specific handler can never run (g++ even warns about it). Correct reasoning: list handlers from most derived to most general: TriangleException before logic_error before exception, and catch (...) (catch anything) last.
    
  
    

  
    
    
    !Common misconception #4
    
    
    "Catching by value, like catch (exception e), works the same as catching by reference."
    
    
    Why it's wrong: catching a derived object by base-class value copies only the base part (called slicing), so the overridden what() is lost.
    
    
    by value: Base
by reference: Derived
    
    
    Correct reasoning: catch by const reference: catch (const Base& e).
    
  
    

  
    Propagation and stack unwinding
    
  
    If a function doesn't catch an exception, it ends immediately and the exception moves to its caller. This is stack unwinding: each exited function's local variables are destroyed on the way out. It continues until a matching handler is found. If none is found, std::terminate ends the program.
    
  
    destroy inner local
destroy outer local
caught 42
    

  
    
    WORKED EXAMPLE
    
    Tracing an exception through three functions
    
    
    a start
b start
c start
main caught: disk full
done
    
    
      
      
    1. Follow the calls down. main calls a, which calls b, which calls c. Each prints its "start" line.Nothing unusual happens until the throw.
      2. 
      
    2. Find the throw. c() throws a runtime_error. "c end" is skipped.Code after a throw in the same block never runs.
      3. 
      
    3. Look for a handler in c, then b. Neither has a try block, so both end immediately. "b end" is skipped.This is stack unwinding: c's and b's frames are destroyed.
      4. 
      
    4. Check a's handler. a catches logic_error. Is a runtime_error a logic_error? No, they are sibling classes. No match, so a ends too, and "a end" is skipped.A try block only helps if one of its handlers matches the type.
      5. 
      
    5. Reach main. catch (const exception& e) matches, because runtime_error derives from exception. "main after a" is skipped, the handler prints, then "done" prints.Execution resumes after the handler that caught it, never back inside c.
      6.

    Rethrowing
    
  
    A handler can do part of the work (like logging) and then pass the same exception up with throw;, or throw a different one with throw expression;.
    
  
    logging: index 9
main: index 9
    

  
    
    
    !Common misconception #5
    
    
    "A function must list the exceptions it throws in its heading, like void f(int x) throw(int, string)."
    
    
    Why it's wrong: these dynamic exception specifications appear in older textbooks, but they were deprecated in C++11 and removed in C++17. Under -std=c++17, g++ reports "ISO C++17 does not allow dynamic exception specifications." Correct reasoning: modern C++ only marks functions that never throw, with noexcept. Document what a function may throw in a comment instead.
    
  
    

  
    

    



    
  
    5. Using Exceptions Well
    
  
    UnderstandAnalyzeEvaluate
    
  
    Three choices when an exception occurs
    
  
    
    
    Terminate the program
    When there is no point continuing.
    Example: a payroll program starts and its required input file does not exist. Print a clear message and exit.
    
    
    Fix the error and continue
    When the user or program can correct the problem.
    Example: a user types a letter instead of a number. Clear the input and prompt again until the entry is valid.
    
    
    Log the error and continue
    When the program must keep running.
    Example: software monitoring a satellite or a nuclear reactor writes the exception to a log file and keeps working.
    
  
    

  
    
    
    ✓Real-world application: importing grades
    
    
    Imagine a tool that imports a CSV of scores into a gradebook. One bad row (a score of 104) should not stop the whole import. The program should skip it, record why, and keep going. That is "log and continue."
    
  
    

  
    Exceptions vs. a simple if
    
  
    
    
    Use exceptions for...
    • Unexpected errors that are detected in one place but handled in another (often across function calls)
    • Errors a constructor can't report through a return value
    • Problems common to several classes in a project
    
    
    Use if / validation for...
    • Expected situations, such as a user typing a menu choice out of range
    • Simple checks handled in the same function
    • Normal control flow: never use throw as a fancy break
    
  
    
  
    The slides' QuotientWithFunction example shows why exceptions matter: without them, quotient() could only print a message and call exit(0), killing the program. With throw, the caller chooses whether to terminate, recover, or log.
