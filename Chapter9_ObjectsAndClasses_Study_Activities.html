Objects and Classes

Six sections walk through how C++ classes and objects work — from core vocabulary through constructors, object behavior, code organization, encapsulation, and class design. Each section ends with a quick self-check. Then head to Flashcards, the Quiz, or the Matching activity to practice.

Object-oriented programming (OOP) means programming using objects. An object represents an entity in the real world that can be distinctly identified — a student, a desk, a circle, a button, even a loan.

🧩 Object

  • Has a unique identity, state, and behavior
  • State = a set of data fields (properties) with their current values
  • Behavior = a set of functions (methods) the object can perform

🏗️ Class

  • A construct that defines objects of the same type
  • Uses variables to define data fields
  • Uses functions to define behaviors
  • Provides constructors — special functions used to construct objects

Think of a class as a blueprint, and each object as one house built from that blueprint — every house (object) has its own address and paint color (state), but they're all built the same way (behavior).

  • A constructor has exactly the same name as the class, has no return type — not even void — and initializes a new object
  • A no-arg constructor takes no parameters, e.g. Circle()
  • If a class declares no constructors at all, C++ implicitly provides a default constructor — a no-arg constructor with an empty body
  • Constructors can be overloaded — multiple constructors with the same name but different parameter lists

Here's the reasoning for creating and using a Circle object:

Memberwise Copy

The assignment operator = copies each data field from one object to another. circle2 = circle1; copies the radius — afterward they're still two separate objects, just with matching values at that moment.

Constant Object Name

Once declared, an object name always refers to that same object — it can't be reassigned to represent a different one. The object's contents can change; its identity cannot.

Anonymous Objects

An object created and used only once doesn't need a name: Circle() or Circle(5.5) creates an anonymous object on the spot.

Class Is a Type

Just like int length; declares an int variable, Circle c1; declares a variable of type Circle. A class is a custom data type.

⚠️ Common Misconception

"After circle2 = circle1;, the two objects stay linked — changing circle1 later will also change circle2." Not true. The assignment performs a one-time memberwise copy: each of circle1's data field values is copied into circle2 at that moment. After the copy, circle1 and circle2 are completely independent objects. Changing circle1's radius afterward has no effect on circle2.

C++ lets you separate a class's definition from its implementation:

  • The class declaration (.h file) lists the data fields, constructor prototypes, and function prototypes — the contract
  • The class implementation (.cpp file) implements the constructors and functions — how the contract is fulfilled
  • Both files share the same base name, just different extensions — e.g. Circle.h and Circle.cpp

Preventing Multiple Inclusions

If a header file gets #included more than once in the same compilation (a common accident when headers include each other), the compiler sees duplicate declarations and fails. The fix is an inclusion guard:

#ifndef CIRCLE_H #define CIRCLE_H class Circle { public: double radius; Circle(); Circle(double); double getArea(); }; #endif

Inline Functions

When a function is implemented directly inside the class declaration, it automatically becomes an inline function. A function only prototyped in the class (and implemented separately in the .cpp file) is a regular function — unless you explicitly mark it inline there too.

⚠️ Common Misconception

"The header and implementation files can be named anything, as long as both get included somewhere." By convention they should share the same base name — only the extension differs (Circle.h / Circle.cpp). This isn't just style: it's what lets any programmer instantly find the implementation that matches a given declaration, and it's the pairing most build tools and IDEs expect.

A public data field like circle1.radius can be modified directly from anywhere — including circle1.radius = -5;, which makes no physical sense. This is risky for two reasons: the data can be tampered with, and the class becomes hard to maintain, because every program that used the field directly (a "client") breaks if you ever need to change how that data is stored.

Accessor (Getter)

returnType getPropertyName()

For a bool, convention uses isPropertyName() instead of getPropertyName().

Mutator (Setter)

void setPropertyName(dataType value)

Can validate the incoming value before storing it — e.g. rejecting a negative radius.

The Scope of Variables

Data fields act like class-wide variables — accessible to every constructor and function in the class, in any declaration order. Local variables, declared inside a function, are only visible within that function. If a local variable shares its name with a data field, the local variable takes precedence and temporarily hides the data field inside that function.

⚠️ Common Misconception

"Making data fields private just adds extra typing — getters and setters don't really change anything." They change quite a lot. Private fields with validated setters let the class enforce its own rules (like "radius can't be negative") in exactly one place, and let the internal representation change later without breaking any client code that only ever called getRadius()/setRadius(). Public fields give up both of those guarantees.

🌍 Real-World Application — A Bank Account Class

Imagine a BankAccount class with a balance data field. If balance is public, any code anywhere in a large banking application could write account.balance = -500; — an overdraft with no record of how it happened, and no way to stop it.

If balance is private with a deposit(amount) and a withdraw(amount) function instead of a raw setter, the class can enforce real business rules — e.g. rejecting a withdrawal that would leave the balance negative — no matter which part of the application calls it. This is exactly why real financial software encapsulates its data.

Class abstraction means separating a class's implementation from the use of the class. The creator of the class provides a description of what the class does and how to use it; the user of the class doesn't need to know how it's implemented internally. The implementation detail is encapsulated and hidden from the user.

🌍 Case Study — The Loan Class

A Loan class might expose functions like getMonthlyPayment() and getTotalPayment(). A programmer using this class in a banking app doesn't need to know the interest formula used internally — they just call the functions and trust the results. If the bank later changes how interest is calculated, the Loan class can be updated internally without changing a single line in any program that uses it, as long as the public functions keep the same names and behavior.
